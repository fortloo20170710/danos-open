# DANOS-Open v0.16 Release Decision

Status date: 2026-11-03 (America/Los_Angeles). Decision candidate:
**HOLD — v0.16.0-rc1 is not qualified and no `v0.16.0` tag may be created.**

This document enumerates the current acceptance rows, their verdict, the
evidence behind the verdict and the exact precondition needed to close an open
row. It is the reviewer's checklist for a final tag; it is not a release
announcement. **No row marked `ENVIRONMENT-OPEN` is qualified, and no
software `PASS` row is a production/performance claim.**

## Verdict definitions

| Verdict | Meaning |
|---|---|
| `PASS` | The stated evidence exists on the merged tree or an identity-bound historical artifact, and the row's functional/software criterion is met. It is not by itself a production qualification. |
| `ENVIRONMENT-OPEN` | The required hardware/topology/runner was unavailable or not rerun, so the row is **not** passed. A green software suite does not substitute for it. |
| `HUMAN-SIGNOFF` | The technical evidence is insufficient by policy alone; a named reviewer/owner must accept the evidence, the residual risk or the waiver. |

A clean release requires every row to be `PASS` with no waiver. Proceeding with
an explicitly waived `ENVIRONMENT-OPEN` row is a different outcome: an
"approved-with-open-lanes" release, recorded as such in the gate result, not a
qualified release.

## What the reviewer must decide before a final `v0.16.0` tag

1. **Attempt or defer the hardware lanes.** Decide whether to obtain the
   L3-01/L3-02 PCI/DPDK runner and the L3-03/L3-04 physical R2/R4 environment
   now, or explicitly defer them. Deferral requires
   `DANOS_RELEASE_ALLOW_OPEN_LANES=1` and produces an approved-with-open-lanes
   release, not a qualified one. The gate's `dpdk_open_waived` and
   `status` fields must record the choice.
2. **Requalify VMware (L2-06/L2-07).** Load the VMware modules, boot the clean
   VMXNET3 pair, capture fresh serial evidence and run the packet gate, or
   explicitly accept that the virtual L2 evidence is historical and waive the
   row.
3. **Rerun live BGP/OSPF (MGMT-15)** on the candidate after the FRR 10.3 type
   corrections, or document a waiver. The static chain PASS does not cover it.
4. **Accept or reject the current L0/L1/L2 evidence as sufficient for a
   release candidate.** If accepted, rerun the unified gate on the exact
   candidate commit and archive the result file.
5. **Security sign-off (REL-01).** Approve production PKI/mTLS or explicitly
   limit the release to lab/test certificates.
6. **Release authority (REL-03/REL-04).** Approve the version/changelog and
   sign the final decision. Only then create the tag; do not tag from a dirty
   tree or from a different commit than the gate result.
