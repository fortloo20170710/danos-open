# v0.16 Performance Result Schema

更新时间：2026-10-09

QEMU、VMware VMXNET3 和真实 PCI DPDK lane 使用 `schema_version=1` 的共同
字段集合；lane-specific scope、stage 和 qualification status 区分功能基线与硬件性能。
缺少硬件或流量发生器时相应资格字段输出 `SKIP` 或 `ENVIRONMENT-OPEN`，
不得写成真实 PCI 性能 PASS；功能 lane 的 `status=PASS` 不代表硬件性能资格。

统一候选发布入口为
`danos-test/integration/run_v016_release_gate.sh`；它汇总 backend contract、
CTest、已验收的 topology-705、QEMU soak result adapter、VMware packet gate 和
DPDK preflight，并生成 gate 与 QEMU lane 机器结果。QEMU/VMware 功能子项可以
`PASS`，同时将真实 PCI 性能标记为 `ENVIRONMENT-OPEN`；但 release gate 在没有真实
PCI qualification 时整体必须为 `FAIL`，除非显式授权 waiver。当前项目未授权 waiver。

实现状态：PCI、VMware 与 QEMU recorder 均输出共同 schema。VMware 从最新完整双路径
ping 周期解析包数、耗时、PPS、MAC-frame Mbps 和 RTT；CPU 未采集时留空。QEMU recorder
核对 manifest ISO digest、串口 clean build identity、四条逐流收发、总时长/PPS、两个
bucket 增量及 soak 后 VPP restart marker；结果记录在
`build/v016-qemu-ecmp-soak.env`。QEMU 的帧长、Mbps、延迟和 CPU 未测量时留空，
`status=PASS` 仅表示功能 soak 验收，`performance_status=ENVIRONMENT-OPEN` 明确表示
不构成真实 PCI 性能资格。PCI 缺少流量发生器时同样保持性能 OPEN。

## Required fields

```text
status=PASS|SKIP|ENVIRONMENT-OPEN|FAIL
schema_version=1
preflight_status=PASS|SKIP|FAIL
performance_status=PASS|ENVIRONMENT-OPEN|FAIL
stage=preflight|packet-baseline|single-core-64b|multi-core|long-stability
lane=qemu-e1000|vmware-vmxnet3-polling|pci-dpdk
commit=<source commit embedded in the measured ISO>
iso_build_commit=<source commit embedded in initramfs build-info.env>
iso_source_dirty=0|1|empty
runner_commit=<checkout commit used for the preflight/recorder>
iso_sha256=<sha256 or empty>
packet_size_bytes=<integer or empty when not measured>
flows=<integer>
packets_tx=<integer>
packets_rx=<integer>
loss_pct=<number>
duration_ms=<integer>
pps=<number>
mbps=<number or empty when not measured>
rtt_p50_us=<number or empty>
rtt_p99_us=<number or empty>
cpu_pct=<number or empty>
ecmp_bucket_0=<integer or empty>
ecmp_bucket_1=<integer or empty>
restart_replay=PASS|SKIP|FAIL
```

对 PCI `single-core-64b` 首轮，必须从 ISO 的 initramfs 读取 build identity，且
`commit == iso_build_commit`、`iso_source_dirty=0`；`runner_commit` 单独记录运行
预检工具的 checkout，不能冒充被测 image commit。缺失 build-info、dirty image 或
身份不匹配时不得签发性能 PASS。`flows` 表示独立 5-tuple 数，必须至少为 2；
一个 5-tuple 通常只命中一个 ECMP bucket。`ecmp_bucket_0/1` 必须表示测量时间窗
内各路径 packet counter 的增量（结束值减开始值），且两者都大于 0；不能拿全局
累计值或测量窗外流量满足条件。结果校验器会拒绝 `flows < 2`。
性能结果录入器还要求 preflight 明确声明 `schema_version=1`；缺少版本或非 v1
输入均拒绝，避免跨 schema 错误解释身份和资格状态。
拒绝记录自身仍使用 schema v1 envelope，并附 `failure_reason`，以便统一消费者在
不接受性能数据时仍能解析结果。

## Interpretation

### Bounded physical peer generator preparation

`danos-test/perf/render_physical_pg.py` renders disabled VPP UDP streams for
an explicit GigabitEthernet NIC-output node. It makes no runtime changes;
rate and count are bounded, count cannot be zero, and at least two distinct
destination flows are required. The intended MAC frame is 64 bytes without
FCS (14 Ethernet + 20 IPv4 + 8 UDP + 22 payload), matching this schema.
Start with low rate and finite count on the isolated R2 peer, never inject
into R3's software input graph as a substitute for physical ingress.

Example preparation (stdout only; not a traffic start command):

```bash
python3 danos-test/perf/render_physical_pg.py \
  --interface GigabitEthernet1/0/0 \
  --source-mac 00:1f:7a:69:f5:ec --target-mac 00:1f:7a:69:f7:4f \
  --source-ip 10.10.0.2 --target 30.30.30.2 --target 30.30.30.3 \
  --rate 100 --count 1000
```

Reference: [official VPP PG documentation](https://docs.fd.io/vpp/25.10/developer/corearchitecture/vnet.html).
VPP 26.10 runtime parsing was verified on the physical serial-connected runner
on 2026-10-10. The first multiline definition failed with CLI line error;
the renderer now emits one complete brace group per line for `vppctl exec`.
Two streams appeared disabled with count 0, limit 1000, rate 100, size 64-64;
both were deleted and the listing returned to no streams. No packets were sent.
Evidence: `build/physical-pg-parse-20261010.serial.log`, SHA256
`1162e7c7bad7f7a53fb4eeedc22449f12843373fd2022b44dea59ecd911ae5c0`.
The preceding QEMU keyboard attempt remains unverified, not a PASS.
Renderer tests additionally lock one complete command per output line.

On 2026-10-10 the serial peer was positively identified as R2 (P1 MAC
`00:1f:7a:69:f5:ec`, address 10.10.0.2/24, VPP main PID 2097). The first
physical NIC-output probe enabled four streams at 10 requested pps, limit 20
each. All four stopped at count 20. R2 hardware TX 12398 → 12478 and bytes
1363680 → 1368800 prove 80 emitted MAC frames and 5120 bytes (64 per frame).
Hardware RX also rose 12398 → 12478; RX packet type has not been captured,
so do not label it as UDP echo, latency or application delivery evidence.
All test streams were deleted; final listing showed no streams.
Raw evidence: `build/r2-physical-pg-probe-20261010.serial.log`, SHA256
`4e5c026b989dbec3886dbda4009e522056eae6802aeedfd9ef18f200dc89bab0`.
This bounded wire-emission check is not a performance qualification: R3
coincident ingress/egress, CPU, actual timing, receiver and latency evidence
remain required. UART return to R3 requested; do not infer its deltas from R2.
Even after runtime acceptance, require R2 hardware TX, R3 hardware RX and
both egress deltas, receiver counts, coincident CPU and independently measured
latency before performance qualification. Requested PG rate is not measured PPS.

### VPP process CPU sampling

`python3 danos-test/perf/collect_vpp_cpu.py --pid <vpp-pid> --duration 10
--out <sample.json>` samples real `/proc/<pid>/stat` ticks against a monotonic
clock. `cpu_pct=100` means one logical CPU; multi-threaded usage may exceed 100
and is never clamped. Process start ticks must remain unchanged; restart or
counter reset invalidates the sample. The JSON explicitly uses
`scope=cpu-sample-only` and `performance_status=ENVIRONMENT-OPEN`. Combine it
with a coincident traffic window and thread/core evidence before qualification;
an idle sample does not satisfy the PCI measurement contract.

The current sampler also reads `vppctl show threads` before and after sampling,
records each thread index/name/LWP/CPU, and checks that the CLI main LWP equals
the sampled PID. A changed mapping, duplicate identity, malformed numeric row,
or CLI error invalidates the sample. `vpp_thread_count` and
`single_dataplane_thread` are evidence fields, not a performance verdict.
The idle sample below predates these additional thread snapshots; do not
retroactively treat it as a full thread-bound sample.

On 2026-10-10, R3 PID 2312 (`/usr/bin/vpp`, one `vpp_main` thread) sampled
10000.607 ms: ticks 1630872 → 1631871 at 100 Hz, CPU 99.89394%.
Remote `/tmp/danos-r3-idle-cpu.json` is the sample, not traffic qualification.
Sampler SHA256:
`c0de22b8803574a4d74b782baa2c15b0d9a2ec71959dc6d53f37748d34c887ff`.
Polling can consume nearly a whole core when idle; do not reuse a low CPU
threshold intended for interrupt-driven workloads or infer forwarding load
from process CPU alone.

- VMware 当前已具备 packet-level baseline：100 packets、10ms interval、0%
  loss、约 99.01/98.04 pps；该结果是回归基线，不是线速结论。
- VMware 结果中的 `packet_size_bytes` 按无 FCS 的 Ethernet MAC frame 计；56-byte
  ICMP payload 对应 98-byte frame。Mbps 仅按该 MAC frame 长度折算，不能代表含
  preamble/IFG 的物理线速。
- 所有 lane 的 `mbps` 统一按十进制 Mbps 计算：
  `pps * packet_size_bytes * 8 / 1,000,000`。因此 PCI 首测使用 64-byte frame，
  VMware ICMP smoke 使用 98-byte MAC frame；QEMU 未测 frame rate 时保持为空。
  录入器按 lane 的 `packet_size_bytes` 解释速率，不能在不同 frame 长度间直接比较
  Mbps；比较 packet processing capacity 时使用 PPS，并同时报告帧长。
- 1000-packet stability run 同样通过：双路径 0% loss、约 97.56/97.47
  pps，VPP 两端口 counters 分别达到约 1007 RX；该结果用于长稳趋势，
  仍不是线速结论。
- `mbps`、CPU、p50/p99 和高强度多流数据必须来自真实流量发生器或专用
  runner，不能由 ICMP smoke 推导。
- `ecmp_bucket_*` 表示本次运行的 counter 增量，不表示绝对累计值。
- QEMU e1000 的 `status=PASS` 只表示 clean-source 功能 soak 通过；其
  `performance_status` 必须保持 `ENVIRONMENT-OPEN`，且不填造包长、Mbps、延迟或 CPU。
- `status=SKIP` 只说明环境未满足前置条件；它不能作为性能通过证据。
- PCI runner 的 `preflight_status=PASS` 只证明指定 BDF、绑定驱动、VPP/DPDK
  plugin 和 HugePages 可用。没有真实流量发生器产出的 PPS、loss、latency、CPU
  与 bucket 计数时，`performance_status` 和总 `status` 必须保持
  `ENVIRONMENT-OPEN`。

## 2026-10-09 VMware default verifier regression

单独调用 VMware verifier 时，默认此前仍指向旧的
`danos.serial.log`/`peer.serial.log` 与非-clean ISO，而统一 release gate 已使用 clean
证据，导致默认调用失败。默认现已统一为 `danos-clean.serial.log`、
`peer-clean.serial.log` 和 `danos-open-v0.16.0-rc1-vmware-vmxnet3-polling-clean.iso`；
`v016_release_gate_config` CTest 锁定这些默认值。无覆盖参数的默认命令重新验收通过：
2000/2000、0% loss、20360 ms、98.23 pps、98-byte MAC frame、0.077014 Mbps，RTT
p50/p99 206/449 us。该数据仍只是低速 ICMP packet regression，不是线速或高强度 ECMP。
