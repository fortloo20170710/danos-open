# v0.16 performance baseline lanes

2026-10-15: archived functional results are now summarized by a repeatable,
read-only lane runner. This does not deploy or access physical routers, bind
NICs, allocate hugepages, launch VPP, or rerun the accepted virtual topologies.
The report hashes its input artifacts and retains their source commits and
measurement dates. These are historical regression baselines, not measurements
of the latest source or sustained hardware capacity.

| Metric | QEMU e1000 | VMware VMXNET3 |
| --- | --- | --- |
| Source commit/date | `b3804e0`, October 10 | `b9c4020`, October 2 |
| Packets received/sent | 4,000/4,000 | 2,000/2,000 |
| Duration | 48.8 s | 20.36 s |
| PPS | 81.97 | 98.23 |
| MAC-frame throughput | Open: frame size absent | 0.077014 Mbps (98-byte frames) |
| RTT p50/p99 | 414.9/3,566.2 µs | 206/449 µs |
| Phase-aligned CPU | Open | Open |
| Recorded ECMP bucket counts | 3,000/1,000 | 9/1,003 |
| Share of recorded bucket counts | 75%/25% | 0.889%/99.111% |
| Bucket counters / total TX | 100% | 50.6% |

ECMP percentages describe only the supplied counters, not hash fairness or
statistical balance. VMware's partial counter coverage cannot establish a
whole-run distribution. RTT is ICMP round-trip latency, not one-way UDP
latency. MAC throughput excludes preamble and inter-frame gap. Missing fields
remain null; idle CPU, simulation, and unrelated measurement windows cannot
fill them. There is no running local VPP process for a new CPU measurement.

## Reproduce the report and PCI preflight

```sh
bash danos-test/perf/run_baseline_lanes.sh
```

Artifacts are written under `build/performance-baselines/`:
`virtual-baselines.json`, `virtual-baselines.log`, `pci-preflight.env`, and
`pci-preflight.log`. Override `BASELINE_OUT_DIR`, `BASELINE_QEMU_RESULT`, and
`BASELINE_VMWARE_RESULT` to select archived artifacts. The runner rejects
invalid counters, nonfinite values, inconsistent PPS/throughput and duplicate
lanes. It does not revalidate the original topology logs or certify input
provenance merely because the input claims PASS.

The local run returned exit 2 with `preflight_status=SKIP`: no target
`DPDK_PCI_BDF` was selected. Physical performance remains `ENVIRONMENT-OPEN`.
The existing real PCI lane is read-only and requires an explicitly selected
Ethernet BDF, matching userspace driver, clean ISO provenance, hugepages,
VPP binaries/plugin and a running VPP instance. On an already provisioned,
authorized runner, supply `DPDK_PCI_BDF`, `DPDK_PCI_DRIVER`, and `DPDK_ISO`.
Do not use deployment or rebinding to make this command pass.

Both native/container preflight and the PCI measurement validator now reject
VMXNET3, virtio, common emulator vendors and e1000/e1000e identities used by
the virtual lanes. Since some Intel IDs overlap real cards, these IDs are
conservatively reserved for functional tests. Passing this exclusion check
alone does not prove physical hardware or that VPP owns the selected BDF.
The preflight continues to return 2 after prerequisite success until traffic
qualification is supplied. `record_dpdk_perf_result.py` requires measured
64-byte packet, loss, latency, CPU and bucket data plus independent receiver
provenance; explicit thresholds are required for performance PASS.

## Capture CPU with a traffic command

The existing CPU sampler now supports a command window:

```sh
python3 danos-test/perf/collect_vpp_cpu.py --pid VPP_PID --duration 120 \
  --out build/cpu-window.json --command /path/to/local-traffic-runner --duration 60
```

Replace `VPP_PID` and the traffic command with an authorized local fixture.
The sampler verifies VPP executable, PID/start-time and CLI thread/core
identity, and brackets the command with monotonic timestamps and process CPU
ticks. `--duration` bounds the command runtime. Output includes command status
and stdout/stderr; a failed command fails the sample. CPU uses one logical CPU
as 100%, so multiple VPP threads can exceed 100%. The window includes command
startup/teardown; the traffic runner must export its own timing to establish
phase alignment. CPU samples alone never assert performance acceptance.

Remaining measurement work: aligned CPU for both virtual lanes, QEMU frame
size/throughput evidence, complete VMware bucket-window coverage, and a real
PCI traffic runner with sustained PPS/throughput, timestamped latency and
CPU/distribution measurements. Physical routers were untouched in this pass.
